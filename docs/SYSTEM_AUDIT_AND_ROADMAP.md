# تقرير الفحص الشامل لنظام ERP وخطة التطوير

تاريخ الفحص: 2026-11-27 — الفرع: `claude/affectionate-newton-3id48n` — آخر commit مفحوص: `07a4f2f`

## 0. الخلاصة

النظام الحالي **واجهة غنية جداً تعمل فعلياً من `localStorage` في المتصفح**، وخلفها Backend يحتوي منطقاً حقيقياً لكنه غير موصول بالواجهة في أهم المسارات (المنتجات، المخزون، البيع، الورديات، الأقساط)، ومكشوف أمنياً بالكامل. لا يصلح للتشغيل الإنتاجي متعدد المستخدمين بوضعه الحالي.

أربع حقائق تحدد كل ما بعدها:

1. **مصدر الحقيقة هو المتصفح لا الخادم.** المنتجات والمخزون والمبيعات محفوظة في `localStorage` لكل جهاز. مسح بيانات المتصفح يمسح المخزون، وجهازان لا يريان نفس الأرصدة.
2. **الـ API مفتوح.** 17 من 36 Controller بلا مصادقة، وهوية المستأجر وصلاحية مدير المنصة تُقبلان من ترويسة HTTP يرسلها العميل.
3. **لا توجد محاسبة حقيقية.** لا دليل حسابات ولا قيد مزدوج؛ أرصدة مخزّنة تُعدَّل مباشرة، وعدة مسارات تغيّر الرصيد بلا قيد، أو تحسبه مرتين، أو لا تحسبه أبداً.
4. **قاعدة البيانات غير قابلة لإعادة البناء من المستودع.** أربع تعريفات متضاربة للمخطط، ولا يوجد نظام migrations، وثمانية جداول يستخدمها الكود بلا تعريف.

### طريقة الفحص وحدودها

- قراءة ثابتة للكود على ستة محاور متوازية (~80 ألف سطر). كل بند موسوم **مؤكد** تم تتبّع مساره في الكود؛ **مشتبه** يحتاج تحققاً على بيئة حية.
- شُغّل في الواجهة: `npm ci`، `tsc -b`، `oxlint`، `vite build`.
- **لم يُشغَّل**: بناء الـ Backend (لا يوجد `dotnet` في بيئة الفحص)، ولا أي قاعدة بيانات، ولا أي اختبار على نسخة تعمل. قاعدة الإنتاج الحية لم تُفحص، فقد تختلف عن ملفات SQL في المستودع.

### 1.2 المصادقة والعزل

- الدخول عبر `POST /api/v1/auth/login`. الترتيب: حالة خاصة لـ `superadmin`، ثم مستخدم القاعدة بصيغة `user@slug`، ثم بحث عبر كل المستأجرين، ثم **قائمة حسابات تجريبية مكتوبة في الكود**.
- كلمات المرور: SHA-256 بلا salt، مع قبول القيمة المخزّنة كنص صريح.
- JWT بتوقيع HS256 لمدة 8 ساعات، والمفتاح نص ثابت في `backend/Program.cs:83`. لا تحقق من issuer أو audience.
- المستأجر يُحدَّد من: claim في التوكن، وإلا ترويسة `X-Tenant-Id`، وإلا `X-Tenant-Slug`.
- العزل يعتمد **فقط** على فلتر EF العام. سياسات RLS موجودة في SQL لكنها غير فعّالة (الخادم لا يضبط `app.current_tenant_id` ويتصل كمالك للجداول).
- الواجهة: عند فشل الاتصال أو أي رد غير 400/401/403 تنتقل لتسجيل دخول محلي من `localStorage`.

### 1.3 تدفق البيانات في الواجهة

`web-dashboard/src/services/storageService.ts` (4,977 سطر) هو قاعدة البيانات الفعلية: ~45 مجموعة في `localStorage` بمفتاح `zilox_tenant_{slug}_*`، وفيه منطق البيع والشراء والمرتجعات والولاء والخزينة والأقساط. الـ "مزامنة" هي `fetch(...).catch(() => {})` بعد الكتابة المحلية: لا طابور، لا إعادة محاولة، لا مفتاح idempotency.

المعرّفات المحلية بصيغة `PRD-1234` و`WH-01`، والخادم يتوقع `Guid`، فطلبات البيع تفشل عند الربط ويُتجاهل الفشل.

| الشاشة | مصدر البيانات |
|---|---|
| المنتجات والمخزون، إضافة/تعديل منتج | محلي فقط |
| نقطة البيع، إنشاء فاتورة، فواتير المبيعات | محلي، والمزامنة ميتة |
| الورديات، الأقساط، الجرد، التحويلات | محلي |
| الوارد، الصادر، التوصيل، أوامر الشراء | محلي (واجهات شكلية) |
| مرتجعات الشراء | محلي عملياً (المسار المستدعى خاطئ) |
| إنشاء موظف، إدارة المستأجرين (SuperAdmin) | محلي |
| التقارير | حساب محلي |
| المشتريات الواردة، الموردون | API أولاً مع إظهار الأخطاء |
| الخزينة، المصاريف، الشركاء، عروض الأسعار، السيريالات، الزبائن والولاء، الإعدادات | هجين |
| سجل التدقيق، بطاقة الولاء العامة، مخطط المستودع الحي | API |

### 1.4 مسارات الأعمال في الـ Backend

- **البيع** (POS والفاتورة العادية يشتركان في `DiscountEngineService.CreatePosInvoiceAsync`): قفل Redis اختياري، معاملة EF واحدة، إعادة حساب السعر في الخادم، خصم من `warehouse_stock` وكتابة `StockMovement`، تكلفة البضاعة = لقطة من `Product.CostPrice`، ضريبة ثابتة 5%، توجيه الدفع (نقد/بطاقة للخزينة، آجل لرصيد الزبون، أقساط لعقد وجدول)، نقاط ولاء، سيريالات.
- **الشراء**: معاملة واحدة تنشئ الفاتورة وتزيد المخزون وتكتب حركة وطبقة FIFO وتخصم من الصندوق وتحدّث ذمة المورد. لا مسودة ولا تعديل، فقط إلغاء.
- **الكمية**: الحقيقة في `warehouse_stock.quantity` (عدد صحيح). سجلّان جزئيان للحركات (`stock_movements` و`inventory_transactions`) ولا واحد منهما كامل.
- **التكلفة**: `Product.CostPrice` يُستبدل بآخر سعر شراء. طبقات FIFO تُكتب ولا تُستهلك أبداً.
- **الأموال**: أرصدة مخزّنة في `cash_boxes.current_balance` و`suppliers.current_balance` و`customers.current_balance`، مع سجل `treasury_transactions` لبعض المسارات فقط.
- **الربح**: يُحسب لحظياً = فواتير `PAID` − تكلفة البضاعة − المصاريف. لا شيء يُحفظ ولا إقفال فترات.
- **Triggers قاعدة البيانات** تعمل على جداول لا يكتب فيها EF، فلا يوجد خصم مزدوج ولا حماية من جهة القاعدة.

### 2.4 حرج — مالية

- **البيع الآجل والأقساط لا يصير إيراداً أبداً.** الفاتورة تُنشأ `UNPAID` (`DES:452`) ولا كود يحوّلها `PAID`، وكل حسابات الربح تفلتر على `PAID`. بيع أقساط 10 ملايين مُحصَّل بالكامل = إيراد صفر.
- **تحديثات ضائعة على كل رصيد.** قراءة ثم كتابة بلا قفل: وصلان متزامنان بـ 100 على رصيد 1,000 ينتجان 1,100.
- **مخطط قاعدة جديدة لا يطابق نموذج EF.** ثمانية جداول بلا تعريف (`staff_users`, `discount_audit_logs`, `installment_contracts`, `installment_schedule_items`, `stock_movement_items`, `inventory_transactions`, `cash_expenses`, `employee_financial_transactions`)، و`sales_invoices` بأعمدة مختلفة، و`warehouse_stock.item_id NOT NULL` بلا قيمة. على نشر جديد: المنتجات والبيع والأقساط والاستلام ترمي أخطاء.
- **تهيئة القاعدة الفارغة على الأرجح لا تُنفَّذ** (مشتبه قوي): `Program.cs:335` يمرر الملف إلى `ExecuteSqlRaw` وفيه أقواس JSON غير مهرّبة، والاستثناء يُسجَّل كتحذير فقط فيقلع الـ API "سليماً" على قاعدة فارغة.

### 2.5 عالٍ — منطق الأعمال

**مبيعات**
- أرقام المستندات عشوائية من 4 أرقام (`INV-yyyyMMdd-1000..9999`) — احتمال التصادم ~50% عند 110 فاتورة يومياً — `DES:440`.
- لا idempotency في POS: إعادة المحاولة تنشئ فاتورة ثانية وخصماً ثانياً.
- تجاوز الحد الائتماني: `CreditLimit == 0` يعني بلا حد، والبيع الآجل باسم مكتوب ينشئ زبوناً جديداً مكرراً بحد 0 — `DES:1270-1288, 1413`.
- ZAIN_CASH و QI_CARD تُسجَّل `PAID` بلا قيد خزينة — `DES:1321-1535`.
- تحويل عرض السعر لفاتورة: دائماً `PAID`، بلا خزينة ولا رصيد زبون ولا حركة مخزون ولا تكلفة؛ كمية 0.5 تُسعَّر 0.5 وتخصم 1 — `backend/Services/QuotationService.cs:299-401`.
- عقد الأقساط المستقل يثق بالعميل كلياً (دفعة مقدمة سالبة مقبولة)؛ تسديد القسط بلا قفل ولا جدول دفعات، وغير النقدي لا يُقيَّد.
- مرتجع فاتورة لم تُصرف من المستودع يضخّم المخزون، والحجز لا يُحرَّر أبداً.
- المستخدم يعتمد مرتجعه بنفسه (`Decision` نص حر من العميل).
- المنتج الذي يتطلب سيريال يُباع بلا سيريال.

**مخزون ومشتريات**
- FIFO للكتابة فقط؛ التكلفة = آخر شراء. 100 قطعة بـ 10 ثم شراء قطعة بـ 20 → التقييم يقفز من 1,000 إلى 2,020 — `backend/Controllers/PurchaseBillsController.cs:487`.
- إلغاء فاتورة شراء يتجاهل الدفعات والمرتجعات اللاحقة: فاتورة آجلة 1,000 تُدفع ثم تُلغى → الـ 1,000 تختفي — `PurchaseBillsController.cs:796-963`.
- مرتجع الشراء النقدي يُحسب مرتين (ينقص ذمة المورد ويزيد الصندوق) — `backend/Services/PurchaseReturnService.cs:302-342`.
- إجماليات فاتورة الشراء من العميل بلا إعادة حساب؛ الكمية 0 أو −5 تصبح 1 بينما `LineTotal` يستخدم القيمة الخام — `PurchaseBillsController.cs:195-258, 423`.
- اعتماد الصرف من المستودع: ضغطتان تخصمان مرتين، و`Math.Max(0, …)` يخفي العجز — `DES:1130-1218`.

**مالية**
- تغيّر الرصيد بلا قيد في السجل: المصروف السريع، معاملات الشركاء، تسديد القسط، دفعة العقد المقدمة، استرداد مرتجع الشراء. أغلبها يختار "أول صندوق فعّال" بلا ترتيب.
- تعدد العملات شكلي: لا جدول أسعار صرف، التحويل بين دينار ودولار 1:1، وعملة الحساب قابلة للتعديل وفيه رصيد — `backend/Controllers/TreasuryController.cs:380-441`.
- الخزينة تصير سالبة بلا فحص.
- أرباح الشركاء: لا شيء محفوظ، تُعاد بنسب اليوم (تغيير نسبة يعيد كتابة التاريخ)، السحوبات بلا سقف — `backend/Services/PartnersService.cs:124-151`.
- معادلتا ربح مختلفتان: `/api/finance/kpis` بالتكلفة الحالية، ولوحة الشركاء بتكلفة وقت البيع؛ والإيراد يشمل الضريبة.
- تأكيد المصروف الدوري مرتين يدفع مرتين.

**قاعدة بيانات وبنية**
- **سكربت حذف يعمل عند كل إقلاع**: `Program.cs:464` يشغّل `17_remove_seeded_expense_categories.sql` الذي يحذف فئات المصاريف ذات الرمز `rent`/`salaries`/… لكل المستأجرين.
- قيود فريدة على مستوى المنصة لا المستأجر (`warehouses.code`, `sales_invoices.invoice_number` …)، والتسجيل يدرج `WH-01` لكل مستأجر → ثاني مستأجر يفشل تسجيله.
- الكميات `int` في EF و`NUMERIC(18,4)` في SQL: البضاعة بالوزن غير ممكنة.
- حذف مستأجر يمسح كل تاريخه المالي بالتتابع (38 مفتاحاً أجنبياً `ON DELETE CASCADE`).
- `docker-compose.yml` لا يعمل: اسم متغير الاتصال خاطئ ومنفذ الواجهة خاطئ.
- لا نسخ احتياطي حقيقي؛ ونسخة المستأجر تغفل المستخدمين والولاء والشركاء والحركات، والاستعادة upsert لا تحذف ما بعدها فتترك الدفاتر غير متسقة.

**واجهة**
- العملة تُخمَّن من حجم المبلغ (`amount > 10000`) بسعر ثابت 1520: بيع 5,000 دينار يُعامل كدولار ويضيف 7,600,000 للخزينة — `storageService.ts:2290, 2325`.
- النقد يُقرَّب إلى 250 لأي عملة: بيع 299.99$ يُسجَّل 250$.
- "إصلاح ذاتي" للخزينة يعيد رصيداً صفرياً مشروعاً إلى مجموع كل الفواتير النقدية — `storageService.ts:2526-2530`.
- 259 `catch` تبتلع الأخطاء، وعمليات كثيرة تعرض "نجاح" مهما رد الخادم (تغيير كلمة مرور، حذف منتج، اعتماد مصروف، إغلاق وردية).
- تجاوز حصة `localStorage` (~5MB) صامت: المبيعات تتوقف عن الحفظ والواجهة تقول "تم".
- الكتابة فوق المصفوفة كاملة عبر التبويبات، مع احتمال تسرّب بيانات مستأجر لمفتاح مستأجر آخر (مؤكد بالمسار، غير معاد إنتاجه).

## 4. خطة التطوير

الترتيب مقصود: كل مرحلة شرط لما بعدها. لا معنى لبناء محاسبة فوق بيانات تعيش في المتصفح، ولا لربط الواجهة بـ API مكشوف.

### المرحلة 0 — إيقاف النزيف الأمني (أيام، قبل أي شيء)

1. FallbackPolicy يفرض المصادقة على كل شيء، و`[AllowAnonymous]` صريح للنقاط العامة فقط.
2. حذف مسارات الترويسات من `TenantProvider`: المستأجر والدور من claims التوكن فقط.
3. مفتاح JWT من متغير بيئة، وتدويره، والتحقق من issuer/audience.
4. حماية `impersonate` بدور PlatformSuperAdmin مع تدقيق.
5. حذف الحسابات التجريبية ومخزن المستخدمين في الذاكرة، وإزالة `superadmin`/`123` لصالح سرّ إقلاع من البيئة مع تغيير إجباري.
6. فحص صلاحية وقائمة أدوار مسموحة في `UsersController`.
7. حذف تسجيل الدخول المحلي من نسخة الويب، ورموز PIN الثابتة من كل الجهات.
8. تدوير مفتاح التراخيص وإزالته من تاريخ git.
9. PBKDF2/Argon2 بـ salt مع إعادة تجزئة عند الدخول؛ rate limiting على الدخول والتسجيل وبطاقة الولاء.
10. إيقاف السكربت 17 عند الإقلاع، وإغلاق Swagger و`/api/config/status` في الإنتاج.

**معيار الإنجاز:** طلب بلا توكن لأي مسار غير عام يرجع 401، وترويسة `X-Platform-SuperAdmin` بلا أثر.

### المرحلة 1 — أساس البيانات والهندسة (2–3 أسابيع)

1. اعتماد EF Migrations كمصدر وحيد للمخطط: baseline من قاعدة الإنتاج الفعلية، وحذف نسخ SQL الثلاث وكل DDL وقت الإقلاع والطلب.
2. قيود فريدة `(tenant_id, …)`، `tenant_id NOT NULL`، `RESTRICT` بدل `CASCADE` على المستأجر، وفهارس `(tenant_id, created_at)`.
3. تسلسل أرقام مستندات لكل مستأجر بدل العشوائي.
4. concurrency tokens (`xmin`) أو تحديثات ذرّية على المخزون والأرصدة، والاستغناء عن Redis كشرط للصحة.
5. معالج استثناءات عام وصيغة خطأ واحدة، DTOs بدل ربط الكيانات، FluentValidation، ترقيم صفحات موحّد.
6. مشروع اختبارات تكامل (Testcontainers + Postgres) يغطي: بيع، مرتجع، شراء، إلغاء، تزامن آخر قطعة، عزل المستأجرين. CI على كل PR.
7. نسخ احتياطي مجدول خارج الخادم مع تجربة استعادة، وفحص صحة يشمل القاعدة، وسجلات منظّمة.
8. تنظيف: حذف الكود الميت ومخرجات البناء الملتزمة، وتصحيح README و`docker-compose.yml`.

**معيار الإنجاز:** قاعدة فارغة + `dotnet ef database update` = نظام يعمل، والاختبارات تمر في CI.

### المرحلة 2 — الخادم مصدر الحقيقة (4–6 أسابيع)

1. نقل المنتجات والمخزون والمستودعات إلى الـ API بمعرّفات UUID، مع أداة ترحيل لبيانات `localStorage` الحالية.
2. جعل البيع معاملة خادم منتظَرة، مع مفتاح idempotency لكل عملية.
3. جداول حقيقية للورديات (فتح، إغلاق، فرق الجرد فقط، تقرير Z محفوظ).
4. نقل الأقساط والتحويلات والجرد وإنشاء الموظفين وإدارة المستأجرين للخادم، وإصلاح المسارات الميتة.
5. استبدال `storageService` بطبقة استعلامات (TanStack Query) وإضافة Router وتقسيم الكود؛ `apiClient` يرمي عند `!res.ok` ويعالج 401.
6. إن كان العمل بلا اتصال مطلوباً: outbox حقيقي في IndexedDB بإعادة محاولة ومفاتيح idempotency وحل تعارض — كميزة مصمَّمة، لا كسلوك احتياطي صامت.
7. تفعيل TypeScript `strict` تدريجياً وإصلاح مخالفات الـ hooks.

**معيار الإنجاز:** مسح بيانات المتصفح لا يفقد شيئاً، وجهازان يريان نفس المخزون لحظياً.

### المرحلة 3 — تصحيح منطق الأعمال (4–6 أسابيع، تتداخل مع 2)

1. **البيع:** رفض الكميات غير الموجبة، سقف وصلاحية لخصم الفاتورة، ربط تجاوز المدير فعلياً بالفاتورة، قيد خزينة لكل طريقة دفع، دفع مقسّم وجزئي، إلغاء فاتورة بعكس كامل.
2. **المرتجعات:** إشعار دائن يعكس الخزينة أو ذمة الزبون والضريبة والخصم والنقاط في معاملة واحدة؛ فصل صلاحية الاعتماد.
3. **الذمم:** سند قبض من الزبون مع تخصيص للفواتير، وتحديث حالة الفاتورة والأقساط، وكشف حساب.
4. **المشتريات:** إعادة حساب الإجماليات في الخادم، تخصيص الدفعات للفواتير، إلغاء يراعي الدفعات والمرتجعات، إصلاح الحساب المزدوج لمرتجع الشراء.
5. **التكلفة:** محرك تقييم واحد (متوسط متحرك أسهل، أو FIFO باستهلاك فعلي للطبقات) يُستخدم في كل خروج ودخول، مع كرت صنف من سجل حركات واحد كامل.
6. **الحجز:** إلغاء أمر الصرف وتحرير الحجز.
7. **الوقت:** كل حدود الفترات بتوقيت المستأجر (Asia/Baghdad).

**معيار الإنجاز:** اختبارات مطابقة تثبت أن مجموع الحركات = الرصيد المخزّن للمخزون والخزينة والذمم بعد أي تسلسل عمليات.

### المرحلة 4 — النواة المحاسبية (6–8 أسابيع)

1. دليل حسابات لكل مستأجر مع قوالب جاهزة، وجدول قيود يومية بقيد مزدوج غير قابل للتعديل (عكس فقط).
2. ترحيل تلقائي من كل مستند: بيع، مرتجع، شراء، قبض، صرف، مصروف، تسوية مخزون، توزيع أرباح.
3. الأرصدة تُشتق من القيود، والأعمدة المخزّنة تصبح كاشاً قابلاً لإعادة البناء.
4. فترات مالية وإقفال وقفل ترحيل.
5. ميزان مراجعة، قائمة دخل، ميزانية عمومية، تدفقات نقدية، أعمار ذمم.
6. تعدد عملات حقيقي: جدول أسعار صرف بتاريخ، عملة المستند وعملة الأساس، فروقات صرف.
7. محرك ضرائب قابل للإعداد.
8. توزيع أرباح الشركاء كمستند محفوظ لكل فترة مقفلة.

### المرحلة 5 — استكمال الوحدات (حسب أولوية السوق)

- **مشتريات:** طلب ← أمر ← استلام ← فاتورة مع مطابقة ثلاثية، تكلفة واصلة، شروط دفع.
- **مخزون:** دفعات وصلاحية، وحدات قياس بمعاملات تحويل وكميات عشرية، مواقع متعددة، تحويل بحالة "في الطريق"، جرد دوري، اقتراحات إعادة الطلب.
- **مبيعات:** أوامر بيع وإشعارات تسليم، قوائم أسعار الزبائن، عروض وكوبونات، فوائد وغرامات وإعادة جدولة الأقساط.
- **موارد بشرية:** ملف موظف، حضور، إجازات، مسيّر رواتب مرحَّل للمحاسبة، عمولات.
- **مالية متقدمة:** تسوية بنكية، مراكز كلفة، موازنات مُلزِمة، أصول ثابتة.
- **تقارير:** تقارير من الخادم قابلة للتصدير.

### المرحلة 6 — المنصة والعملاء

- MFA، refresh tokens، إبطال جلسات، استعادة كلمة المرور، فحص حالة الاشتراك لكل طلب.
- تفعيل RLS فعلياً كخط دفاع ثانٍ (دور غير مالك + `FORCE` + متغير جلسة عبر interceptor).
- اختيار حل سطح مكتب واحد (الـ WPF هو الوحيد الذي فيه طباعة وترخيص) وحذف البقية.

- توحيد i18n على مفاتيح الترجمة.
- بيئة staging وخطة نشر مدفوعة بنسخ احتياطي.

### مخاطر الخطة وقرارات مطلوبة منك

1. **هل يوجد عملاء على الإنتاج الآن؟** إن نعم، فالمرحلة 0 عاجلة جداً، وترحيل بيانات `localStorage` في المرحلة 2 يصبح أخطر بند في الخطة.
2. **هل العمل بلا اتصال مطلب حقيقي؟** القرار يغيّر حجم المرحلة 2 كثيراً.
3. **طريقة التقييم:** متوسط متحرك أم FIFO.
4. **ما حالة قاعدة الإنتاج الفعلية؟** الـ baseline في المرحلة 1 يعتمد عليها، ولم تُفحص.
